# Kironomics Hook Reference

Read this when the user asks how the hooks work internally, wants to inspect or hand-edit the hook file, is migrating from the 0.x hook format, or needs the per-workspace fallback.

## Installed layout

```
~/.kiro/
├── kironomics/
│   ├── kironomics_counter.py   (PostToolUse + UserPromptSubmit)
│   ├── kironomics_report.py    (Stop)
│   └── config.json             (API key + backend URL, mode 600)
└── hooks/
    └── kironomics.json         (all three global hooks, v1 format)
```

Nothing is written into any workspace.

## The global hook file

`~/.kiro/hooks/kironomics.json`, generated by the installer. Paths shown for macOS and Linux; on Windows they are absolute Windows paths with the interpreter resolved at install time.

```json
{
  "version": "v1",
  "hooks": [
    {
      "name": "Kironomics Tool Counter",
      "description": "Counts tool calls for the Kironomics leaderboard.",
      "trigger": "PostToolUse",
      "matcher": ".*",
      "action": {
        "type": "command",
        "command": "\"/usr/bin/python3\" \"/Users/you/.kiro/kironomics/kironomics_counter.py\" tool"
      },
      "timeout": 5,
      "enabled": true
    },
    {
      "name": "Kironomics Prompt Counter",
      "description": "Counts prompts and records session start time.",
      "trigger": "UserPromptSubmit",
      "action": {
        "type": "command",
        "command": "\"/usr/bin/python3\" \"/Users/you/.kiro/kironomics/kironomics_counter.py\" prompt"
      },
      "timeout": 5,
      "enabled": true
    },
    {
      "name": "Kironomics Session Reporter",
      "description": "Reports the finished session to the Kironomics backend.",
      "trigger": "Stop",
      "action": {
        "type": "command",
        "command": "\"/usr/bin/python3\" \"/Users/you/.kiro/kironomics/kironomics_report.py\""
      },
      "timeout": 15,
      "enabled": true
    }
  ]
}
```

`PostToolUse` fires after each tool call, `UserPromptSubmit` on each prompt, and `Stop` when the agent finishes its turn. The `matcher` is a regex tested against the tool name, so `.*` matches every tool. It only applies to `PostToolUse`.

Every path is absolute and points at the user's home directory rather than a workspace. That is the mechanism the whole design rests on: a home path is stable for the life of the machine, so one hook file serves every project. Workspace hooks still take precedence over global ones if a project defines a hook with the same name.

## Why an installer instead of shipping hooks with the power

Powers can ship a `steering/` directory, and Kiro loads it. Powers cannot ship hooks. A `hooks/` directory in a power repo is copied to `~/.kiro/powers/installed/<name>/hooks/` during install, but Kiro does not load hooks from that path. This is tracked upstream in kirodotdev/Kiro issue #9007, which is open.

Until that lands, writing `~/.kiro/hooks/kironomics.json` from an installer script is the only way to get global hooks from a power.

## How tracking works internally

Tracking is passive and silent. Both scripts print nothing and always exit `0`, so they add no noise to the agent's context and never block a tool call or a prompt.

During a session:

- `UserPromptSubmit` increments the prompt counter and records the session start time on the first prompt.
- `PostToolUse` increments the tool counter after every tool the agent calls.
- Counters are plain files in the OS temp directory, named `kironomics_<key>_<name>` where `<key>` is a 10-character SHA1 prefix of the hook's working directory. Because global hooks fire in every window, this keying is what stops two open Kiro windows from pooling into one bogus session. If the working directory cannot be read, everything falls back to a single shared bucket, which is no worse than the per-workspace hooks this replaces.
- Counters older than 24 hours are discarded on the next hook, so a crashed or force-quit window cannot inflate the following session.

When the agent finishes and `Stop` fires:

- The reporter reads the counters for this workspace only.
- It opens `state.vscdb` read-only and immutable, and extracts `currentUsage`, `usageLimit`, `percentageUsed` and `resetDate`.
- Sessions with no activity at all are skipped, so no empty requests are sent.
- It POSTs one batched request to `{api_base}/kironomics/session`.
- TLS is verified using certifi's CA bundle when available, falling back to the system default. If the machine has no working CA bundle, or a corporate proxy presents a re-signed certificate, it retries once unverified so the report still lands. The payload is only usage counts, over HTTPS.
- Counters are cleared afterwards even when the request failed, so an outage cannot compound into one giant implausible session.

## Migrating from the 0.x hook format

IDE 1.0 changed the hook system. Anyone upgrading from 0.x will have leftover files in the old format.

| 0.x | 1.0 |
|---|---|
| One `.kiro.hook` file per hook | One JSON document with a `hooks` array |
| `when.type` / `then.type` | `trigger` / `action` |
| `promptSubmit` | `UserPromptSubmit` |
| `postToolUse` | `PostToolUse` |
| `agentStop` | `Stop` |
| `runCommand` | `{"type": "command"}` |

Legacy files appear in the Agent Hooks panel with an upgrade badge and do not execute until migrated. The installer writes the v1 format and prunes the legacy files, so an upgrade plus one install completes the migration.

## Per-workspace fallback

Only for users who decline the Kiro upgrade. It has to be repeated in every workspace, which is the exact problem the global install solves. Say so plainly rather than presenting it as an equivalent option.

Create `.kiro/kironomics_report.py` and `.kiro/hooks/kironomics.json` inside the workspace, with the reporter's absolute path from `pwd` baked into the `Stop` hook command. On a pre-1.0 Kiro, use the 0.x schema instead: one `.kiro.hook` file per hook, `when.type` of `promptSubmit`, `postToolUse` or `agentStop`, and `then.type` of `runCommand`.

## API endpoints

Exactly one endpoint is called from the user's machine.

| Method | Path | Purpose |
|---|---|---|
| POST | `{api_base}/kironomics/session` | Batched session data, sent by the reporter on `Stop` |

`api_base` defaults to the hosted endpoint and is stored in `~/.kiro/kironomics/config.json`. Every other endpoint the project exposes (leaderboard, metrics, heatmap, badges, profile) is called by the dashboard in the browser, never by the hooks.
